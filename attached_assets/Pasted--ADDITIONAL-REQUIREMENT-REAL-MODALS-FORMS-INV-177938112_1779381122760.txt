==================================================
ADDITIONAL REQUIREMENT — REAL MODALS, FORMS, INVOICES, PRINTING, VIEWING, EDITING
==================================================

In addition to all previous requirements, inspect every frontend page carefully.

For every page that currently does not have its own proper modal, drawer, dialog, or form, you must create the correct UI flow for that page.

Each page must have real forms and real action modals according to its business function.

Examples:
- Products page must have Add Product, Edit Product, View Product, Delete Product confirmation.
- Categories page must have Add Category, Edit Category, View Category, Delete Category confirmation.
- Suppliers page must have Add Supplier, Edit Supplier, View Supplier, Delete Supplier confirmation.
- Customers page must have Add Customer, Edit Customer, View Customer, Delete Customer confirmation.
- Users page must have Add User, Edit User, View User, Assign Role, Change Status, Delete User confirmation.
- Branches page must have Add Branch, Edit Branch, View Branch, Delete Branch confirmation.
- Purchase Orders page must have Create Purchase Order, Edit Purchase Order, View Purchase Order, Receive Purchase Order, Cancel Purchase Order, Print Purchase Invoice.
- Sales Orders page must have Create Sales Order, Edit Sales Order, View Sales Order, Refund Order, Print Sales Invoice.
- POS page must have Checkout confirmation, Payment modal, Receipt preview, Print receipt.
- Inventory page must have Stock Adjustment form, View Stock Movement, Transfer Stock form if applicable.
- Tasks page must have Add Task, Edit Task, View Task, Assign Task, Change Status, Add Comment, Delete Task confirmation.
- Expenses page must have Add Expense, Edit Expense, View Expense, Delete Expense confirmation.
- Revenues page must have Add Revenue, Edit Revenue, View Revenue, Delete Revenue confirmation.
- Audit Logs page must have View Details modal.
- Settings page must have editable forms that persist changes.

All forms must:
- Use real validation.
- Show Arabic validation messages.
- Submit to real backend endpoints.
- Save data in the PostgreSQL database.
- Show loading state while submitting.
- Show success/error toast after the backend response.
- Reset or close only after successful backend response.
- Refresh the related list/table after successful changes.

All view modals must:
- Load real data from the backend.
- Show full entity details.
- Show related data where useful.
- Show audit/activity history where applicable.

All edit modals must:
- Load the existing record from the backend.
- Pre-fill the form with real current data.
- Save updates through a real PUT/PATCH endpoint.
- Persist changes in the database.

All delete actions must:
- Open a confirmation dialog.
- Explain clearly what will happen.
- Call a real DELETE endpoint.
- Use soft delete when appropriate.
- Write to audit logs.

==================================================
REAL INVOICES AND RECEIPTS
==================================================

All invoices, receipts, order previews, printing, and exports must be real.

Do not create fake static invoice designs.

Invoices must be generated from actual database records.

Required invoice types:
- Sales Invoice
- POS Receipt
- Purchase Invoice
- Return/Refund Invoice
- Payment Receipt if applicable
- Stock Adjustment Report if applicable

Each invoice must include:
- Company/tenant name
- Branch name
- Invoice number
- Invoice date and time
- Customer or supplier data where applicable
- Created by user
- Items table
- Quantity
- Unit price
- Discount
- Tax if applicable
- Total
- Payment method
- Notes
- Status
- QR code or barcode if useful
- Printable layout

Invoice numbers must be generated by backend logic, not hardcoded in frontend.

Printing requirements:
- Print button must print the real invoice or receipt.
- Preview button must show the real invoice/receipt before printing.
- Export PDF button should export the real invoice/receipt if possible.
- Export Excel/CSV should export the real currently filtered data if applicable.
- Printed layout must be clean, Arabic RTL, and suitable for A4 or receipt printer depending on document type.

All invoice actions must be connected to real backend endpoints.

Examples:
- POST /api/pos/checkout should create a real POS transaction and receipt.
- GET /api/pos/transactions/:id/receipt should return real receipt data.
- GET /api/sales-orders/:id/invoice should return real sales invoice data.
- GET /api/purchase-orders/:id/invoice should return real purchase invoice data.
- POST /api/sales-orders/:id/refund should create real refund data and refund invoice.
- GET /api/invoices/:id should return real invoice details.

==================================================
REAL VIEW, SEARCH, FILTER, EDIT, DELETE
==================================================

All listing pages must support real backend-based operations:

- Real search
- Real filters
- Real sorting
- Real pagination
- Real view details
- Real edit
- Real delete
- Real status change
- Real export
- Real print where applicable

Do not use frontend-only filtering for main data unless the data was intentionally fetched from the backend and the result is still consistent.

For large lists, use backend query parameters:
- page
- limit
- search
- sortBy
- sortOrder
- status
- branchId
- dateFrom
- dateTo

Example:
GET /api/products?page=1&limit=20&search=milk&sortBy=createdAt&sortOrder=desc

==================================================
NO FAKE UI ACTIONS
==================================================

Every button, dropdown action, menu item, and form submission must be audited.

If an action exists visually in the UI, it must either:
1. Be fully implemented and connected to the backend/database, or
2. Be removed, or
3. Be clearly marked as "Coming Soon" and disabled.

Do not leave buttons that show fake success messages.
Do not mutate only local frontend state for business data.
Do not show hardcoded invoice data.
Do not show fake dashboard statistics.
Do not show fake print previews.

The final system must behave like a real ERP demo version, where all pages, forms, modals, invoices, printing, viewing, editing, deleting, searching, filtering, and CRUD operations are connected to real backend APIs and persisted in the PostgreSQL database.
